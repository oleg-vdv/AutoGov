# Техническое задание (ТЗ)
## Governance-платформа для self-hosted-автоматизаций «Control Plane для теневой автоматизации»

**Рабочее название продукта:** *(placeholder)* AutoGov / ShadowFlow Control
**Версия ТЗ:** 0.1 (черновик для MVP)
**Статус:** проект, обсуждается

---

## 1. Назначение и цели

### 1.1. Проблема
Бум self-hosted-автоматизаций (в первую очередь n8n: 230 000+ активных пользователей, оценка $1,5 млрд в середине 2025, рост mid-market-клиентов ~10× за год именно в self-hosted-сегменте) создаёт новый класс неучтённой ИТ-инфраструктуры. Сотрудники самостоятельно поднимают инстансы n8n в Docker на рабочих станциях и серверах, зашивают в них боевые креды (API-ключи, OAuth-токены, доступы к 1С/CRM/БД) и запускают воркфлоу без ведома ИТ/ИБ. Для службы безопасности это «unknown unknown»: точка утечки с прямым доступом к продакшн-системам, невидимая для существующих инструментов.

Существующие Shadow IT / SaaS-discovery-инструменты (Microsoft Defender for Cloud Apps, Nudge Security, Auvik и др.) ищут **SaaS/OAuth-подключения**, но не видят **локально развёрнутые автоматизации**. Специализированного вендора по governance для self-hosted n8n на рынке нет.

### 1.2. Цель продукта
Дать ИБ/ИТ-отделу единый «control plane», закрывающий весь жизненный цикл теневой автоматизации по формуле **найти → задокументировать → защитить → чинить**:
- **M1 — Обнаружение** (идея №19): найти все инстансы автоматизаций и оценить их риск.
- **M2 — HoneyNodes** (идея №21): встроить приманки и детектировать компрометацию.
- **M3 — Self-healing** (идея №27): автоматически восстанавливать упавшие воркфлоу и заводить тикеты с патчами.
- **M4 — Автодокументация** (идея №29): генерировать актуальную карту сети/зависимостей и Swagger.

### 1.3. Стратегический принцип разработки (главная развилка проекта)
**MVP = только модуль M1 (Обнаружение)**, но архитектура с первого дня проектируется как **платформа с подключаемыми модулями (plugin-based)**. Причина: каждый модуль по отдельности имеет узкий TAM, и попытка сделать все четыре сразу растянет разработку и распылит фокус. При этом если M1 написать как монолит «под себя», то M2–M4 придётся переписывать. Поэтому:
> Требование ТЗ-0: ядро (агент + control plane + модель данных + шина событий) реализуется универсальным; M1 — первый «вертикальный срез» поверх этого ядра, доказывающий, что M2–M4 встанут как плагины без переработки ядра.

Это ключевой архитектурный инвариант, к которому в документе будут отсылки.

## 2. Термины и сокращения

| Термин | Значение |
|---|---|
| **Инстанс** | Запущенный экземпляр движка автоматизации (n8n, Make-агент, скрипт-раннер и т.п.) |
| **Актив (Asset)** | Обнаруженный объект инвентаризации: инстанс, воркфлоу, credential-ссылка, хост |
| **Находка (Finding)** | Зафиксированный факт с риск-оценкой (например, «инстанс n8n с доступом к 1С на ноутбуке вне ИТ-периметра») |
| **Control Plane** | Центральный сервер платформы: агрегация, риск-скоринг, UI, API |
| **Агент (Sensor)** | Компонент, разворачиваемый на хосте/в сети, выполняющий сбор данных |
| **Credential-ссылка** | Метаданные о секрете (тип, целевая система, отпечаток), **без значения самого секрета** |
| **ПДн** | Персональные данные (в контексте Закона РК № 94-V) |
| **SUL** | Sustainable Use License — лицензия n8n |

## 3. Область применения и ограничения

### 3.1. В охвате MVP (M1)
- Обнаружение инстансов **n8n** (self-hosted, приоритет №1 как самый частый и самый опасный кейс).
- Обнаружение обобщённых автоматизаций: контейнеры Docker с триггер-паттернами, процессы Node.js/Python-раннеров, задачи `cron`/`systemd timers`, воркфлоу-файлы.
- Инвентаризация, риск-скоринг, карта «инстанс → какие креды → к каким системам доступ».

### 3.2. Вне охвата MVP (закладывается архитектурно, реализуется позже)
- M2 (HoneyNodes), M3 (Self-healing), M4 (Автодокументация) — только точки расширения и контракты API.
- Автоматическое реагирование/блокировка (в MVP — только обнаружение и оповещение; активные действия — отдельная фаза с отдельными рисками).

### 3.3. Правовые ограничения (обязательны к учёту)
- **Лицензия n8n (SUL):** продукт **не хостит n8n как сервис для третьих лиц** и не перепродаёт n8n. Продукт работает с **уже развёрнутыми** клиентом инстансами (инспекция, а не хостинг). Текст SUL проверить построчно до релиза — это условие непопадания под ограничение.
- **Локализация ПДн (Закон РК № 94-V):** сам продукт работает с чувствительными данными о инфраструктуре и потенциально с ПДн. Для клиентов из РК control plane и хранилище находок должны иметь **on-prem / внутристрановой** режим; агент **не должен вывозить значения секретов и содержимое ПДн за периметр**. Отправка чего-либо во внешние сервисы (включая внешние LLM) = трансграничная передача → в on-prem-режиме запрещена по умолчанию.

### 4.2. Ключевые архитектурные решения (и почему)

**Разделение «Агент ↔ Control Plane».** Агент только собирает и нормализует данные локально; вся аналитика (скоринг, корреляция, модули) — в control plane. Почему: (1) агент должен быть максимально лёгким и легко аудируемым (он работает с высокими правами — см. §9), (2) это позволяет добавлять модули M2–M4 на стороне control plane **без обновления агента**.

**Плагинная модель модулей (Module Runtime).** Модули M1–M4 — это отдельные плагины поверх общей шины событий и общего хранилища активов. Каждый модуль подписывается на нужные типы событий и публикует находки в единый формат. Почему: это и есть реализация Требования ТЗ-0 — M1 доказывает контракт, M2–M4 встают без переписывания ядра.

**Событийная шина (Event Bus).** Агенты шлют «сырые наблюдения» (raw observations); модули их потребляют. Почему: развязывает сбор от анализа и даёт естественные точки расширения (M3 self-healing подпишется на события ошибок воркфлоу, M2 — на события обращения к приманкам).

**Outbound-only агент, mTLS.** Агент сам инициирует исходящее соединение к control plane (никаких входящих портов на хостах-сенсорах). Почему: не расширяем поверхность атаки на защищаемых машинах — иначе продукт про безопасность сам станет уязвимостью (типичная ошибка подобных инструментов).

### 4.3. Варианты сбора данных: агентный vs безагентный (сравнение)

| Подход | Плюсы | Минусы | Решение для MVP |
|---|---|---|---|
| **Агентный** (демон на хосте) | Видит локальные процессы, `.n8n`, `cron`, Docker-сокет; работает и на не-сетевых инстансах | Нужно разворачивать и обновлять; требует прав | **Основной для MVP** — только так видно теневые инстансы на рабочих станциях |
| **Безагентный сетевой** (скан подсети) | Быстрый охват, ничего не ставить | Видит только сетевые инстансы (порт/HTTP), не видит локальные `localhost:5678` без внешнего доступа; риск ложных срабатываний | **Дополнительный** — как быстрый первичный охват серверов |

> Типичная ошибка: сделать только сетевой скан. Тогда самый частый и опасный кейс — инстанс на `localhost:5678` на ноутбуке сотрудника, доступный только локально, — останется невидимым. Агент обязателен.

## 5. Функциональные требования — Модуль M1 «Обнаружение» (MVP)

### 5.1. Методы обнаружения n8n (техническая спецификация)

Агент должен детектировать инстанс n8n по совокупности признаков (не по одному, чтобы снизить ложные срабатывания):

1. **Docker-инспекция.** Через Docker API / `docker ps`: образы `n8nio/n8n`, `docker.n8n.io/n8nio/n8n`; проброс порта `5678`; переменные окружения `N8N_*` (`N8N_ENCRYPTION_KEY`, `DB_TYPE`, `WEBHOOK_URL`); связанные контейнеры `postgres`/`redis` (queue mode).
2. **Процессы.** Node.js-процессы с сигнатурой n8n; Python-раннеры и планировщики с признаками автоматизаций.
3. **Сетевой фингерпринт.** Открытый порт **5678** (default) → HTTP-проверка: наличие эндпоинтов **`/api/v1`** (public REST API, аутентификация заголовком `X-N8N-API-KEY`), внутреннего **`/rest`** (используется веб-редактором, session/JWT), Swagger-плейграунда **`/api/v1/docs`**, а также `/healthz`/`/webhook` паттернов. Комбинация этих путей однозначно идентифицирует n8n.
4. **Файловая система.** Каталог `~/.n8n` (`config`, база SQLite по умолчанию), `docker-compose.yml` с сервисом n8n, `.env` с `N8N_ENCRYPTION_KEY`.
5. **Планировщики.** Записи в `cron`, `systemd timers`, запускающие раннеры автоматизаций.

> Важно: агент фиксирует **факт наличия** `N8N_ENCRYPTION_KEY` и целевые системы, но **не извлекает и не передаёт значение ключа** и не расшифровывает креды. Это принципиальное ограничение приватности (§9).

### 5.2. Инвентаризация (Asset inventory)
- Для каждого инстанса: хост, пользователь-владелец (по возможности), способ запуска (Docker/npm/systemd), версия, статус (running/stopped), сетевая доступность (localhost-only / LAN / публичный), тип БД (SQLite/PostgreSQL), режим (single/queue).
- Для каждого воркфлоу (если доступен public API с ключом, предоставленным клиентом-администратором, либо чтение конфигурации): список нод, наличие webhook-триггеров, внешние интеграции.

### 5.3. Карта «инстанс → креды → целевые системы»
- Определить, к каким внешним/внутренним системам обращается инстанс (по типам credential-ссылок и HTTP-нодам): 1С, CRM, БД, платёжные API, облака.
- Построить граф достижимости: какой теневой инстанс имеет доступ к каким продакшн-ресурсам. Это основной артефакт ценности для CISO.

### 5.4. Риск-скоринг
Модель оценки риска находки (пример весов, настраиваемый):
- Доступ к продакшн-системам (1С/платежи/БД клиентов) — высокий вес.
- Публичная сетевая доступность инстанса — высокий вес.
- Наличие webhook-триггеров, открытых наружу — средний/высокий.
- Инстанс вне ИТ-инвентаря (владелец — не ИТ) — повышающий коэффициент.
- Устаревшая версия n8n с известными CVE — повышающий коэффициент.
- Итог: числовой скор + категория (Critical/High/Medium/Low) + человекочитаемое объяснение «почему».

> Требование: каждая находка сопровождается объяснением на естественном языке (для отчёта CISO и для обучения). В on-prem-режиме объяснения генерируются локально (шаблоны / локальная модель), без отправки во внешние LLM.

### 5.5. Оповещения и отчётность
- Интеграции оповещений: e-mail, Telegram, вебхуки, **syslog/CEF для SIEM (Wazuh, Splunk)** — у продукта естественная синергия с SOC.
- Экспорт отчёта об инвентаре и рисках (PDF/CSV/JSON).
- Дашборд: список инстансов, карта доступа, топ-риски, динамика (появление новых теневых инстансов во времени).

### 5.6. Whitelisting / управление ложными срабатываниями
- Возможность помечать легитимные (санкционированные ИТ) инстансы как «известные», исключать DevOps-контейнеры по правилам.
> Типичная ошибка: без хорошего whitelisting продукт «кричит» на легитимные CI/CD-контейнеры и теряет доверие. Управление ложными срабатываниями — требование первого релиза, а не «потом».

## 6. Функциональные требования — модули M2–M4 (архитектурный задел, вне MVP)

Реализуются позже, но контракты закладываются сейчас, чтобы доказать плагинную модель:

- **M2 HoneyNodes (идея №21).** Подписка на события «обращение к приманочной ноде/ключу/decoy-таблице» → находка «вероятная компрометация инстанса» → алерт в SIEM. Контракт: модуль публикует honey-триггеры и потребляет события доступа.
- **M3 Self-healing (идея №27).** Подписка на события ошибок воркфлоу (через `Error Trigger`/перехват) → предложение патча маппинга/JSON → тикет с диффом. Контракт: потребление событий ошибок, публикация «предложенных исправлений». По умолчанию режим «предлагаю, применяет человек» (безопасность прежде всего).
- **M4 Автодокументация (идея №29).** По данным инвентаря и анализу трафика между контейнерами → карта сети/зависимостей + Swagger. Контракт: чтение Asset Store, публикация артефактов-документов.

> Проверка платформенности: если хотя бы один из M2–M4 нельзя добавить без изменения ядра/агента — архитектура M1 спроектирована неверно и подлежит доработке до релиза MVP.

## 7. Модель данных (основные сущности)

- **Host** — хост-сенсор (id, ОС, сеть, метки).
- **Instance** — обнаруженный движок автоматизации (тип, версия, способ запуска, сетевой профиль, владелец, статус).
- **Workflow** — воркфлоу внутри инстанса (ноды, триггеры, интеграции).
- **CredentialRef** — ссылка на секрет: тип, целевая система, отпечаток (hash), **без значения**.
- **Reachability** — ребро графа «инстанс → целевая система».
- **Finding** — находка с риск-скором, объяснением, статусом (new/acked/whitelisted/resolved).
- **Event** — сырое наблюдение от агента / событие модуля (для шины и аудита).
- **Report** — сгенерированный отчёт.

> Принцип «privacy by design»: в модели данных **нет полей для хранения значений секретов и содержимого ПДн**. Хранятся только метаданные и отпечатки.

## 8. Нефункциональные требования

### 8.1. Производительность и масштаб
- Один агент: потребление CPU в простое < ~2%, полное сканирование хоста < ~60 c при периодичности по расписанию.
- Control plane: инвентарь до ~10 000 инстансов на MVP-инсталляции без деградации UI (пагинация, асинхронная загрузка).

### 8.2. Надёжность
- Агент устойчив к недоступности control plane (буферизация наблюдений, дозапись при восстановлении связи).
- Идемпотентность ingest (повторная отправка не плодит дубли находок).

### 8.3. Совместимость
- Хост-агент: Linux (Ubuntu/Debian/RHEL-семейства) как приоритет; Windows — второй этап (теневые инстансы часто на рабочих станциях, поэтому Windows важен, но после Linux-MVP).
- Развёртывание: Docker/Docker Compose; control plane — контейнеризован.

### 8.4. Приватность и локализация (критично для КЗ)
- Режим **on-prem / внутристрановой** обязателен: весь control plane и хранилища находок разворачиваются внутри периметра/страны клиента.
- В on-prem-режиме **исходящий трафик во внешние сервисы (включая внешние LLM) запрещён по умолчанию** и требует явного включения администратором с предупреждением о трансграничной передаче.

## 9. Требования безопасности самого продукта (повышенный приоритет)

Продукт про ИБ и работает с высокими правами — его собственная безопасность критична.

- **Наименьшие привилегии агента.** Агенту нужен доступ к Docker-сокету, списку процессов, ФС и сетевым проверкам. Доступ к Docker-сокету = фактически root-эквивалент, поэтому: read-only режим по умолчанию, отдельная сервисная учётка, документированный минимальный набор прав, возможность работы без Docker-сокета (деградация функций вместо требования root).
- **Агент не читает значения секретов.** Только факт наличия, тип и целевую систему. Расшифровка кредов n8n **не выполняется никогда**.
- **Подписанные артефакты.** Агент и обновления подписаны; проверка подписи на стороне хоста.
- **mTLS** между агентом и control plane; агент только исходящие соединения.
- **Аудит-лог** всех действий control plane (кто что смотрел/менял) — и для комплаенса, и для расследований.
- **Защита от использования продукта как инструмента разведки.** Ролевой доступ (RBAC): карта «доступ к продакшн-системам» — чувствительный артефакт, доступ к ней ограничен.

## 10. Требования к развёртыванию

- **SaaS** (multi-tenant) — для не-регулируемых клиентов, быстрый онбординг.
- **On-prem / Single-tenant** — для банков, госсектора, регулируемых (обязательно для клиентов РК из-за локализации ПДн).
- **Air-gapped** — опционально, второй этап (для критической инфраструктуры).
- Инсталляция control plane: Docker Compose (MVP), Helm/Kubernetes (позже).

## 12. Критерии приёмки MVP (Э1)

MVP считается принятым, если на тестовом периметре с намеренно развёрнутыми «теневыми» инстансами система:
1. Обнаруживает **≥ 95%** запущенных инстансов n8n (Docker, npm, localhost-only, LAN) при **≤ 5%** ложных срабатываний после whitelisting.
2. Для каждого инстанса строит карту «креды → целевые системы» и присваивает корректную риск-категорию.
3. Не извлекает и не передаёт ни одного значения секрета (проверяется аудитом трафика агента).
4. Разворачивается в on-prem-режиме без единого исходящего соединения во внешние сервисы.
5. Формирует отчёт (PDF/JSON) и шлёт находки в Wazuh через syslog/CEF.

## 13. Риски и открытые вопросы

- **Платформенный overhead vs скорость MVP.** Риск переинженерить ядро в ущерб срокам. Митигация: ядро минимальное, но с явными контрактами; «плагинность» = чёткие интерфейсы, а не сложный фреймворк.
- **Конкурентный ответ.** Крупный EDR/CNAPP-вендор (CrowdStrike, Wiz, Microsoft) может добавить «local automation discovery». Митигация: глубина по автоматизациям (маппинг доступа, а не просто инвентарь процессов) + локализация под КЗ/СНГ.
- **Права агента как барьер продаж.** ИБ-отделы настороженно ставят агентов с доступом к Docker-сокету. Митигация: open-source агент (аудируемость), read-only по умолчанию, подпись.
- **Лицензия n8n (SUL)** — проверить построчно, что инспекция чужих инстансов не подпадает под ограничения (не хостинг n8n).
- **Закон РК № 256-VIII по ИИ** (в силе с 11.07.2026) — проверить, накладывает ли он требования на продукт, использующий ИИ-компоненты (риск-объяснения, будущий M3). Требуется юридический разбор первоисточника.

## 14. Что нужно решить до старта (вход в разработку)
